# 🌐 GLOBAL.md — Главные правила проекта для ИИ-агентов и разработчиков

> [!IMPORTANT]
> Настоящий документ является **высшим авторитетом** в проекте `tg-shopper-bot`. Любой ИИ-агент или разработчик, приступая к работе с репозиторием, **обязан** неукоснительно следовать установленным здесь правилам.

---

## 🎯 Правило №1: Обязательное тестирование (Mandatory TDD & Verification)

> [!CAUTION]
> **Любое изменение без тестов считается браком.**
> На **каждое исправление багов, рефакторинг или новую реализацию** функциональности Агент **ОБЯЗАН**:
> 1. Написать или обновить автоматические тесты в директории `test/` (например, `test/testParser.js` или новый тест-файл).
> 2. Запустить тесты командой `npm test` и убедиться в их успешном прохождении (`exit code 0`).
> 3. Завершение задачи разрешено **только после подтверждения успешного прогона тестов**.

## 🏛️ Архитектурные слои и границы ответственности

В проекте реализована строгая слоистая архитектура:

```
[ Telegram Layer ] ➔ handlers, keyboards, messages
        │
        ▼
[ Service Layer ]  ➔ productService, trackingService, ozonParserService, notificationService
        │
        ▼
[ Repository Layer]➔ productRepository, subscriptionRepository, priceHistoryRepository
        │
        ▼
[ Database / ORM ] ➔ Sequelize Models (Product, Subscription, PriceHistory) + Umzug Migrations
```

### Строгие запреты:
1. **Запрещен прямой доступ к БД**: Ни один файл из `src/telegram` или `src/services` не имеет права выполнять прямые запросы к моделям Sequelize или писать SQL. Любое обращение к данным происходит **исключительно через методы репозиториев** из `src/repositories`.
2. **Инкапсуляция моделей**: Методы репозиториев возвращают чистые JavaScript-объекты (`.toJSON()`), изолируя бизнес-логику от внутренней реализации ORM.
3. **Бизнес-логика только в Сервисах**: Telegram-хэндлеры не содержат вычислений или бизнес-логики. Их задача: валидировать ввод пользователя, вызвать сервис, вернуть отформатированный ответ.

## 🗄️ База данных и миграции

1. **Только через миграции**: Любые изменения таблиц, добавление полей или индексов выполняются **исключительно через новые файлы миграций** в `src/database/migrations/` с использованием `Umzug`.
2. **Формат имени миграции**: `YYYYMMDDHHMMSS-<название>.js`.
3. **Обязательные поля**:
   - Поле **`last_parsed_at`** (`lastParsedAt` в модели) обязательно присутствует в таблице `products` и обновляется при каждом парсинге страницы.
   - Таблицы должны поддерживать внешние ключи с каскадным удалением (`ON DELETE CASCADE`).

## 🕷️ Парсинг Ozon и работа с Puppeteer

1. **Освобождение ресурсов**: Любое открытие вкладки браузера должно быть обернуто в блок `try ... finally { await page.close(); }`, чтобы предотвратить утечки оперативной памяти.
2. **Использование системного Chrome**: Парсер в первую очередь использует системный бинарник `/usr/bin/google-chrome`.
3. **Поддержка Proxy**: При работе на зарубежных хостингах/серверах Ozon применяет геоблокировку дата-центров. Парсер обязан поддерживать переменную окружения `PROXY_URL` с авторизацией.
4. **Демо-режим**: Для локального тестирования без сетевых блокировок в `ozonParserService` должен быть предусмотрен реалистичный демо-генератор цен (`DEMO_MODE=true`).

## 💬 Telegram Bot & UX

1. **Безопасность**: Весь входящий пользовательский текст, попадающий в сообщения, обязан экранироваться через `escapeHtml()`.
2. **Информирование о статусе**: При длительных фоновых задачах (парсинг через Puppeteer) пользователю сразу отправляется промежуточное сообщение («🔍 Загружаю цену...»), которое затем редактируется.
3. **Дата парсинга в карточке**: В карточке товара (`/list` и карточка добавления) всегда выводится точная дата последнего парсинга.
